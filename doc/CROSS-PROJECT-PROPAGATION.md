# 프로젝트 간 전파 (Cross-Project Propagation)

> 작성 2026-07-28 · 갱신 2026-08-02 · 상태: **운용 중 — 대장 14행 (열림 9 / 보류 1 / 닫힘 4)**
> 열림 9 내역: 수신측 검토 필요 5 · 역방향 이식 2 (P1-5·P1-7) · jangbogo 내부 2 (P1-6·P1-9)

**이 문서는 PUBLIC 저장소에 있다.** 로컬 절대경로, 비공개 저장소의 이름·내부 구조·파일 경로·
자격증명·고객명은 적지 않는다. 이쪽(jangbogo) 코드 위치는 저장소 기준 상대경로 + 줄번호로 적고,
**수신측 위치는 적지 않는다** — 대장 번호로만 가리키고 실제 매핑은 수신측 사본이 갖는다.

> **왜 이렇게 나눴나 (2026-08-02 결정).** 초판은 수신측의 모듈 배치·클래스명·줄번호를 그대로
> 적고 있었다. 그건 비공개 저장소의 내부 지도이며, 미확인 결함 항목은 좌표가 붙은 약점 목록이
> 된다. 대장의 운용 가치(무엇이 열려 있는가)는 번호만으로 유지되므로, **판정과 상태는 공개하고
> 수신측 좌표는 비공개로 내렸다.**

## 1. 목적과 범위

이 프로젝트에 외부 자동화 패키지를 import 하는 방안은 폐기했다. 이유는 두 가지다. 첫째,
공개 저장소가 비공개 저장소를 빌드 타임 의존으로 삼으면 CI·외부 기여자·릴리스 수령자 모두에게
**재현 불가능한 빌드**가 된다. 둘째, 발행 좌표에 브라우저를 모는 concrete 구현이 없어 **목표
기여도가 0** 이었고 오히려 재구현 부채만 늘었다.

(초기 검토에는 라이선스 사유도 적혀 있었으나, 2026-08-02 에 배포 형태를 다시 따져 본 결과 그
서술은 결합을 전제한 낡은 것이었다. 폐기 결정을 지탱하는 것은 위 두 가지다.)

**대신 채택한 것이 전파다.** 코드 의존은 두지 않고, 한쪽에서 나온 버그 수정·기능 개선이 다른
쪽에도 **적용 검토**되도록만 한다. 강제 적용이 아니라 검토 의무이며, 두 저장소를 한 사람이
유지하므로 절차는 최소로 둔다. 새 도구·이슈 트래커·라벨 체계를 도입하지 않는다 — 양쪽 다
GitHub 이슈 실사용이 0 이라 도입 즉시 사문화된다.

범위: 브라우저 자동화 공통 표면(드라이버 옵션·클릭·대기·프로필), 무음 실패/감지 부재 계열,
설정·스키마 정본 이중화. 범위 밖: 쇼핑몰 파서, `jbg_*` 스키마, 트레이/WinSW 배포, UI 문구.

## 2. 전파 절차

기존 관행에 얹는다. 새로 만드는 것은 이 문서(대장) 하나뿐이다.

### 2.1 판정 기준 (후보 필터)

한 문장 기준: **"이 결함이 브라우저를 모는 코드라면 프로젝트와 무관하게 재현되는가?"** 예면 후보다.

| 후보다 | 후보가 아니다 |
|---|---|
| 드라이버 옵션 조립·전달, headless 결정, 타임아웃 설정 | 쇼핑몰별 셀렉터·파싱 로직 |
| 클릭 가로채기·대기 전략·오버레이 대응 | `jbg_*` 테이블 스키마 자체 |
| 실패가 예외가 아닌 정상 반환값으로 흡수되는 자리 | 트레이 앱·WinSW·설치 배포 스크립트 |
| 프로필/락/동시성 등 프로세스 간 자원 경합 | UI 문구, 번역, 릴리스 노트 |
| 설정·스키마의 정본이 두 곳에 복제된 자리 | 코드 의존을 전제로만 성립하는 개선안 |
| 운영 중 실제로 발생한 장애의 재발 방지책 | 이미 상대가 대응한 것 (대장에서 확인) |

후보가 아닌 것은 **대장에 올리지 않는다.** 후보인데 상대가 이미 대응했으면 **판정만 남기고 닫는다**
(재조사 방지가 대장의 두 번째 목적이다).

### 2.2 기록 위치와 형식

기록은 **한 곳**이다 — 이 문서의 §3 대장. 그 외에는 기존 그릇에 한 줄씩만 남긴다.

| 시점 | 어디에 | 무엇을 |
|---|---|---|
| 이쪽에서 변경이 커밋될 때 | 해당 버전의 `CHANGELOG.md` `### Notes` | 한 줄. 예: "safeClick 도입은 상대측에도 적용 검토 대상으로 전파됨(대장 P1-5)" |
| 같은 시점 | 해당 항목의 `DEVLOG.md` `#### 메모` | 한 줄. 판단 근거·후속만 |
| 같은 시점 | 이 문서 §3 대장 | 행 1개 추가 (또는 기존 행의 상태 갱신) |
| 사례가 서술을 요구할 때만 | 수신측 저장소에 사례 문서 1개 | 첫 사례가 이 형태다 (§3 OPS-2026-05-30 행) |

`### Notes` 는 이 프로젝트의 CHANGELOG 가 이미 "영향 범위·발행 여부"를 적는 데 쓰는 로컬 확장
슬롯이므로 새 섹션을 만들지 않는다. 커밋 메시지는 **관행대로 `v<x.y.z>: 제목`** 을 유지하고,
제목이나 본문에 `(전파 P1-N)` 처럼 대장 번호를 넣어 검색 가능하게 한다.
`Co-Authored-By:` trailer 는 붙인다.

> **규칙: 공개 산출물에는 대장 번호만 쓴다.** `CHANGELOG.md`·`DEVLOG.md`·커밋 메시지는 전부
> PUBLIC 이다. 거기에 **상대 저장소 이름을 쓰지 않는다** — 번호와 이름이 한 문장에서 만나는
> 순간 대장 전체가 역매핑 가능해지고, 좌표를 비공개로 내린 의미가 사라진다. "상대측"·"수신측"
> 같은 일반 표현을 쓰고, 어느 저장소인지는 수신측 사본이 안다.
>
> 이 규칙은 **실제로 어긴 뒤에 세운 것이다.** v0.13.6 의 `### Notes` 한 줄이 대장 번호와
> 저장소 이름을 함께 적었다(2026-08-02 에 정정).

### 2.3 검토 결과 처리

수신측이 내리는 판정은 셋뿐이다. 어느 쪽이든 **대장 행의 `판정`·`상태` 컬럼 갱신으로 끝난다.**

| 결과 | 대장 표기 | 추가로 남기는 것 |
|---|---|---|
| 적용 | 판정 `전파` / 상태 `닫힘(적용)` | 수신측 CHANGELOG 항목에 출처 표기. 코드가 착지한 시점에만 |
| 해당 없음 | 판정 `해당없음` / 상태 `닫힘` | 왜 성립하지 않는지 한 줄 (근거 위치는 수신측 사본에) |
| 이미 대응됨 | 판정 `이미대응` / 상태 `닫힘` | 재조사 방지가 핵심이므로 판정 사유만 남긴다 |
| 보류 | 판정 유지 / 상태 `보류` | 재검토 조건을 한 줄로 (날짜가 아니라 **조건**으로 적는다) |

`보류` 에 날짜를 적지 않는 이유: 한 사람이 유지하므로 기한은 지켜지지 않고, 조건("프로필 재사용
도입 이후", "본체 저장소를 로컬에 확보한 뒤")이 실제 트리거로 작동한다.

### 3.1 대장이 말하는 것

- Phase 1 의 9건 중 **상대측에 새로 올릴 전파 항목은 0건이었다.** 새로 열린 것은 매핑 과정에서
  나온 파생 관찰 3건(D-1·D-2·D-3)이다. 관찰 내용과 확인 방법은 수신측 사본에만 둔다.
- 9건 중 실질이 남는 P1-5·P1-7·P1-8 은 전부 **역방향** — 상대가 이미 해결한 것을 이쪽이
  내려받는 쪽이다. Phase 1 은 실질적으로 "상대 → 이쪽 이식"이었다.
- P3-1 은 그 뒤 처음으로 열린 정방향 항목이다. 타임아웃을 브라우저 분기마다 따로 설정하는
  구조는 프로젝트와 무관하게 재현되므로 §2.1 필터를 통과한다.

### 3.2 Phase 1 수정 순서 주의 (내부, 전파와 무관하나 대장에 남긴다)

P1-1·P1-2·P1-3 은 서로를 은폐하고 있었다. 당시 순 관측 동작은 "항상 headed" 인데, P1-1(options
전달)만 먼저 고치면 P1-2·P1-3 이 남은 상태에서 "항상 headless" 로 뒤집힌다. **순서는 P1-3 →
P1-2 → P1-1** 로 고정하고 커밋마다 브라우저가 실제로 뜨는지 육안 확인했다.

## 4. 역방향도 같은 대장에서 다룬다

**같은 대장, 별도 표 없음.** 판정 컬럼의 `역방향` 값으로 구분한다.

이유는 실측이다 — Phase 1 의 9건 중 실질이 남은 3건이 전부 역방향이었다. 방향별로 표를 나눴다면
같은 항목(P1-5 `safeClick`)이 두 표에 중복 등재되거나, 방향을 잘못 잡은 채로 한 표에만 남았을
것이다. `jangbogo 변경` 컬럼은 "이쪽에서 관측된 결함"이고, 저쪽이 우위면 그 행이 곧 이식 대상이
된다. 컬럼 의미는 그대로 두고 판정만 뒤집으면 되므로 표를 나눌 이유가 없다.

역방향 항목의 상태 `닫힘` 조건은 이쪽 코드에 반영된 시점이며, 그때 해당 버전의 `### Notes` 에
"상대측에서 이식(대장 P1-N)" 한 줄을 남긴다.

## 5. 운영 규칙

| 질문 | 답 |
|---|---|
| 언제 검토하는가 | **push(=버전) 시점.** `CLAUDE.md` 가 이미 push 마다 CHANGELOG+DEVLOG 갱신을 의무로 두므로, 그 자리에서 §2.1 필터를 한 번 통과시키고 대장 행을 쓴다. 별도 주기 점검·캘린더 없음 |
| 수신측은 언제 보는가 | **세션 시작 시.** 수신측 저장소는 세션 축으로 운영되므로, 그쪽 사본의 열린 항목을 세션 백로그로 옮기는 것이 유일한 운반 수단이다 |
| 누가 | 단독 유지. 리뷰어·승인자 없음 |
| 미검토 항목은 어떻게 드러나는가 | §3 대장의 `상태 = 열림` 행. 이 문서 상단 상태줄에 열린 건수를 적어 둔다 |
| 릴리스를 막는가 | 막지 않는다. 전파는 검토 의무이지 릴리스 게이트가 아니다 |
| 도입하지 않는 것 | GitHub 이슈·라벨·PR 템플릿을 전파 추적 수단으로 쓰지 않는다. 양쪽 다 이슈 실사용 0 이고, 단일 유지자·비공개 수신자 구조에서 이슈 기반 절차는 첫 주에 사문화된다 |

### 5.1 이 문서를 PUBLIC 저장소에 두는 것에 대한 판단 — **2026-08-02 재검토 완료**

초판은 "상대경로+줄번호만 쓰고 커밋" 을 선택하고 사례가 3건을 넘으면 재검토하기로 했다.
**재검토 결과 그 기준은 충분하지 않았다.** 문제는 경로의 형태(절대/상대)가 아니라 **무엇을
가리키는가**였다 — 상대경로라도 비공개 저장소의 모듈 배치·클래스명·줄번호를 적으면 그건
내부 지도이고, 거기에 "미확인" 결함을 붙이면 좌표가 딸린 약점 목록이 된다.

**그래서 이렇게 나눴다.**

| 공개(이 문서) | 비공개(수신측 사본) |
|---|---|
| 대장 번호, 일자, 이쪽 변경 요약 | 수신측을 가리키는 모든 것 |
| 이 저장소 자신의 코드 위치 | 파생 관찰(D-N)의 실제 내용과 확인 방법 |
| 판정·상태, 절차와 운영 규칙 | |

운용 가치는 번호와 상태만으로 유지된다 — "무엇이 열려 있는가"를 push 시점에 확인하는 것이
이 대장의 목적이고, 그 답에 수신측 좌표는 필요 없다.

**단, 이 익명화는 앞으로만 유효하다.** 이 저장소의 커밋 이력과 일부 기존 문서 항목에는 상대
저장소 이름과 과거의 로컬 절대경로가 이미 들어 있다(2026-07-28 의 죽은 포함 빌드 선언 제거를
설명하는 대목이 대표적이다). 즉 **여기서 이름을 지운다고 과거 노출이 없어지지는 않는다.**
이 나눔이 하는 일은 (1) 앞으로 좌표·결함 목록이 더 쌓이지 않게 하고, (2) 대장이 비공개
저장소의 내부 지도로 자라지 않게 막는 것이다. 그 이상을 주장하지 않는다.

공개된 이력을 되감는 것(히스토리 재작성)은 이미 배포된 저장소를 깨뜨리는 조치라 여기서
자동으로 하지 않는다. 필요 여부는 노출된 것이 무엇인지 보고 따로 판단할 일이다 — 현재
드러난 것은 저장소 이름과 개발 PC 의 프로젝트 경로이며, 자격증명이나 내부 코드는 아니다.

세션 인계용 계획서 2건도 같은 판단으로 **정본을 비공개 저장소로 옮기고 이 저장소에서는
`.gitignore` 처리했다.** 세션 인계 문서는 성질상 운영 환경 세부와 미완 작업이 섞이므로,
공개본을 따로 관리하는 것보다 정본을 비공개에 두는 편이 유지 비용이 낮다.
