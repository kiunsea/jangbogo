# ADR-0003 — `--login=<mallId>` 런처 모드를 세션 캡처에 흡수한다

- 상태: **확정 · 종결**(흡수). 대가로 실사용 공백 하나를 명시적으로 수용한다
- 일자: 2026-08-07
- 대상: Phase 5-6′ (런처 로그인 모드) · 5-15 (세션 캡처) · 5-13 (UI 안내)
- 선행: [ADR-0002](ADR-0002-session-capture-path.md) — 캡처 경로를 후보 (a) 로 확정한 측정

## 배경

계획 단계에서 "사람이 한 번 로그인해 세션을 만든다" 를 **런처 모드**로 두는 안이 있었다 —
`Jangbogo.jar --login=<mallId>` 로 그 몰의 로그인 브라우저만 띄우는 전용 진입점이다. 그 자리는 오래
`[개정]` 상태로 방치돼 있었다: *"5-15 에 흡수되거나 그 CLI 진입점으로 축소된다."*

방치된 `[개정]` 은 비싸다. 다음에 오는 사람이 **만들다 만 것**으로 읽고 마저 만들려 들거나, 반대로
이미 있는 줄 알고 찾다가 시간을 쓴다. 그래서 종결한다.

## 확인한 사실 (코드)

| 확인 | 결과 |
|---|---|
| `src/main` 의 CLI 인자 파싱 | **0건.** `JangbogoLauncher.determineExecutionMode` 가 보는 것은 `--service` 하나뿐이고 나머지는 그대로 Spring 으로 넘어간다 |
| `Jangbogo-Login.bat` | **존재하지 않는다.** 저장소 어디에도 없다 |
| `--login` 문자열 | `src/main` 에 **0건** |
| 사람이 로그인해 세션을 뜨는 경로 | **화면에 이미 있다** — 계정 연결 모달의 '브라우저로 로그인' → `POST /mall/session/start` → `SessionCaptureController` → `SessionCaptureService` |

즉 5-6′ 는 **만들다 만 것이 아니라 만들어진 적이 없고, 그 목적을 5-15 가 이미 수행하고 있다.**

## 결정

**5-15 에 흡수하고 종결한다.** 별도 CLI 진입점을 새로 만들지 않는다.

같은 일을 하는 진입점을 둘 두면 화면 경로와 CLI 경로가 각자 낡는다. 캡처는 킬스위치·관리자 세션 창 상한·
단일 활성 제약·고아 브라우저 리퍼를 **전부 서비스 계층에서** 걸고 있는데, CLI 진입점은 그중 관리자 세션이
없어 창 상한 규칙부터 다르게 만들어야 한다. 두 벌이 되는 순간 한쪽만 고쳐지는 것은 시간 문제다.

## 🔴 이 결정이 수용하는 공백 — 배포(서비스) 모드에서 캡처에 도달할 수 없다

**이것이 이 ADR 의 존재 이유다.** 흡수는 공짜가 아니다.

경로가 코드로 닫혀 있다 —

1. 서비스 xml(`packaging/winsw/jangbogo-service.xml`)의 `<arguments>` 가 `... --service` 로 앱을 띄운다.
2. `JangbogoLauncher.launchServiceMode` 가 `jangbogo.launch.mode=service` 를 시스템 프로퍼티로 심는다
   (`--service` 는 Spring 으로 넘어가기 전에 걸러지므로, 이 신호가 없으면 컨텍스트 안의 코드는 자기가
   서비스로 떴는지 알 방법이 없다).
3. `ExecutionContextDetector` 가 그것을 `SERVICE_SESSION_0` 으로 판정한다. `canRunHeadedBrowser()` 는
   `INTERACTIVE` 일 때만 true 다 — **세션 0 에는 데스크톱이 없어 사람이 볼 수 있는 창을 띄울 수 없다.**
4. `SessionCaptureService.start` 는 그 컨텍스트를 보고 **무조건 `REQUIRES_USER_SESSION` 으로 막는다.**

이 차단 자체는 옳다. 막지 않으면 증상이 "실패" 가 아니라 **로그인 화면에서 멈춘 채 타임아웃**으로 나타나고,
로그만으로는 프로필이 잘못됐는지 세션이 만료됐는지 애초에 띄울 수 없는 자리인지 구분할 수 없다.

문제는 **평소 배포 형태가 바로 그 서비스 모드**라는 것이다. 사용자가 트레이/브라우저로 대시보드를 열고
'브라우저로 로그인' 을 누르면, 그 요청을 받는 프로세스는 세션 0 의 서비스이므로 **정상 설치 상태에서
캡처가 한 번도 성공하지 못한다.** CLI 진입점이 있었다면 서비스를 건드리지 않고 별도 프로세스로 캡처할 수
있었을 것이다. 흡수를 택하면서 그 길을 닫았다.

### 그래서 반드시 따라와야 하는 것 — 사용자 안내문

`REQUIRES_USER_SESSION` 이 나올 때 화면에 다음이 함께 보여야 한다.

> **서비스를 중지하고 `Jangbogo.bat` 으로 실행한 뒤 다시 시도하세요.**

지금 메시지는 *"브라우저를 띄울 수 없는 실행 환경입니다. 사람이 로그인한 세션에서 실행해야 합니다."* 다.
**사실은 맞지만 사용자가 할 일이 없다** — '사람이 로그인한 세션' 이 무엇인지, 자기 PC 를 어떻게 그 상태로
만드는지가 안내되지 않는다. 이 문장이 빠진 채로 두면 사용자는 기능이 고장 났다고 판단한다.

넣을 자리는 5-13(UI)에서 처리한다. 이 ADR 은 **그 안내가 선택이 아니라 이 결정의 조건**임을 고정한다.

## 대안과 그것을 택하지 않은 이유

| 대안 | 왜 아닌가 |
|---|---|
| CLI 진입점을 만든다 | 캡처의 제약(킬스위치·창 상한·단일 활성·리퍼)을 두 벌로 만들게 된다. 한쪽만 낡는 것은 시간 문제다 |
| 서비스 모드에서도 캡처를 허용한다 | 세션 0 에는 데스크톱이 없다. 허용하면 실패가 조용한 타임아웃으로 바뀐다 — ADR 이전 상태로 되돌아간다 |
| 서비스를 자동으로 멈췄다 켠다 | 앱이 자기를 띄운 OS 서비스를 조작하는 것이고, 실패 시 되살릴 주체가 없다. 사용자가 명시적으로 하는 편이 안전하다 |

## 되짚어야 할 조건

이 종결은 **무인 재로그인이 필요해지면 다시 열린다.** 세션 수명(5-17)이 짧게 나와 사람이 자주 다시
로그인해야 한다면, "서비스를 중지하고 bat 으로 다시 띄우라" 는 절차의 비용이 기능을 못 쓸 만큼 커진다.
그때 후보는 CLI 진입점이 아니라 **서비스와 별개로 도는 캡처 전용 실행 형태**다.
