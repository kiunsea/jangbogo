# ADR-0002 — 세션 캡처를 어느 브라우저에서 하는가 (5-15)

- 상태: 측정 완료 · **후보 (a) 로 확정**(잰 범위 안에서. 아래 "판단")
- 일자: 2026-08-05
- 대상: Phase 5-15 (세션 캡처) · 5-16 (스냅샷 저장)
- 선행: [ADR-0001](ADR-0001-session-profile-reuse-t3.md) 미해결 1

## 배경

ADR-0001 이 전략을 "프로필 재사용"에서 "세션 이관"으로 바꾸면서 **미해결 1**을 남겼다.

> **캡처를 어디서 하나.** 후보는 두 가지다 —
> (a) 사람이 자동화 브라우저 안에서 로그인한다(로그인 시점에 봇 방어를 만난다)
> (b) 순정 chrome.exe 를 `--remote-debugging-port` 로 띄우고 CDP 로 붙어 쿠키만 뜬다(브라우저 자체는 순정).
> **(b) 가 유력하나 미측정이다.**

5-15 의 나머지(계정 연결 화면·저장·암호화)가 전부 이 선택 위에 얹히므로 먼저 쟀다.

## 먼저 정정한 것 — 캡처 시점

계획서는 5-15 를 "사람이 로그인하면 CDP 로 세션을 떠서 저장한다"고 적었고, 6차 세션의 런처는 **창이 닫힌 것**을
완료 신호로 삼았다(프로필 락 해제). 그러나 ADR-0001 이 확인한 대로 **인증 쿠키가 세션 스코프**라 창이 닫히면
사라진다. 즉 **닫힌 뒤에는 뜰 것이 없다.**

⇒ 캡처는 브라우저가 **살아 있는 동안** 해야 한다. 프로필 락 해제는 완료 신호가 아니라 **정리** 신호다.
이 어긋남은 조용하다 — 락 해제 뒤에 뜨면 매번 빈 스냅샷이 나오는데 어디에서도 예외가 나지 않는다.

## 측정

실계정을 쓰지 않는다. 로컬 페이지가 세션 쿠키(만료 없음 — 우리가 옮기려는 것과 같은 종류)와 영속 쿠키를 심고,
자기 시점의 `navigator.webdriver` 를 보고한다. 대조군과 양성 대조군을 **같은 실행**에 둔다.

재현: `./gradlew test -PincludeProbe --tests '*SessionCaptureProbe*'` (실계정 불필요)

| 팔 | `navigator.webdriver` |
|---|---|
| **[대조군]** 순정 chrome.exe, 포트 없음 | `false` |
| 순정 chrome.exe + `--remote-debugging-port` | **`true`** |
| 붙은 뒤 (같은 문서 / 새 문서) | `true` / `true` |
| 붙은 뒤 마스킹 주입 → 새 문서 | `false` |
| **[양성 대조군]** Selenium 기본 (마스킹 없음) | `true` |
| **[후보 a]** Selenium + 우리 마스킹 | `false` |

함께 확인한 것:

| 항목 | 결과 |
|---|---|
| 붙어서 살아 있는 세션 캡처 | **성립** (세션 쿠키 포함) |
| 뜬 세션을 다른 브라우저에 주입 → 그 브라우저가 들고 있는가 | **예** |
| `driver.quit()` 후 사람의 브라우저 | **살아 있다** (창을 뺏지 않는다) |
| `closeAttachedBrowser`(CDP `Browser.close`) | **닫힌다** |
| 브라우저가 도는 동안 프로필 사용 중 판정 | `true` (Windows 도 `lockfile` 을 만들고 배타적으로 잡는다) |

## 발견 — 후보 (b) 의 전제가 깨진다

**`--remote-debugging-port` 를 여는 것 자체가 자동화 표식을 켠다.** 같은 실행에서 포트 없는 순정은 `false`,
포트를 연 순정은 `true` 였다. 즉 후보 (b) 의 근거였던 *"브라우저 자체는 순정"* 이 **사람이 로그인하는 그 시점에는
성립하지 않는다.**

양성 대조군이 `true` 를 냈으므로 이 측정이 항상 `false` 를 뱉는 고장이 아니라는 것도 함께 확인됐다.

## 남은 결정 — (a) 와 (b) 중 무엇으로 가는가

측정 뒤 두 후보의 차이가 크게 줄었다. **둘 다 마스킹이 필요하고, 둘 다 마스킹 후에는 같은 값을 보인다.**

| | (a) Selenium + 마스킹 | (b) 순정 + 포트 + 붙기 + 마스킹 |
|---|---|---|
| 첫 문서부터 깨끗한가 | **예** | 아니오 — 붙어서 마스킹을 넣기 전까지 켜져 있다 |
| 디버깅 포트 노출 | 없음 | 있다(같은 PC 의 다른 프로세스가 붙을 수 있다) |
| 구성 요소 | 기존 경로 그대로 | 포트 대기 + 붙기 + 종료 수단이 추가로 필요 |
| chromedriver 흔적 | 있다 | 없다(로그인 브라우저 자체에는) |

### 추가 측정 — 12축 지문 비교 (같은 프로브, 실계정 불필요)

`navigator.webdriver` 한 축만으로는 "표식이 없다"를 믿을 수 없어, 순정과 (a) 를 **12축**으로 나란히 쟀다.
`webdriver` · `ua` · `uaTail` · `platform` · `langs` · `plugins` · `cores` · `chromeKeys` · `brands` ·
`uaFull` · `webgl` · `perm`.

**처음 재니 3축이 갈렸고, 셋 다 한 줄에서 나왔다** — `buildChromeOptions` 의 UA 하드코딩이다.

| 축 | 순정 | 후보 (a) — 수정 전 |
|---|---|---|
| `ua` | `Chrome/150.0.0.0` | `Chrome/124.0.6367.91` |
| `uaTail` | `Safari/537.36` | `Safari/537.3` (형태 자체가 어긋나 있었다) |
| `uaFull` | `150.0.7871.187` | **빈 값** |

마지막 항목이 특히 나쁘다. UA 문자열을 덮어써도 **클라이언트 힌트는 실제 버전을 그대로 낸다.** 사이트는 정교한 분석
없이도 '자기를 124 라고 주장하면서 힌트는 150 인' 자기모순을 본다.

T2 의 "지문 동등성 PASS" 와 모순되지 않는다. T2 가 잰 네 축(`webdriver`·`chromeRuntime`·`plugins`·`languages`)에
**UA 쌍이 없었다.** 다른 것을 잰 것이다.

### 수정 — UA 하드코딩 제거

지정하지 않으면 Chrome 이 자기 버전을 정확히 광고한다. 박아 둘 이유도 없었다 — **그 값을 읽는 코드가 저장소에 없고,
도입 커밋(초기 대규모 리팩토링)에도 근거가 없다.**

제거 후 다시 쟀다.

| 항목 | 결과 |
|---|---|
| 지문 12축 비교 (순정 vs 후보 a) | **전부 일치** |
| headless 의 UA | `Chrome/150.0.0.0` — `HeadlessChrome` 를 드러내지 않는다 |

headless 확인이 필요했던 이유는, UA 를 박아 둔 그럴듯한 동기가 "헤드리스 노출 은폐"였을 수 있어서다. `--headless=new`
는 그것을 드러내지 않으므로 그 동기도 성립하지 않는다.

프로브가 이 상태를 계약으로 고정한다 — 지문이 한 축이라도 갈리거나 headless 가 스스로를 드러내면 실패한다.

### 판단

**후보 (a) 로 간다.** 잰 범위 안에서 순정과 구분되지 않고, 포트를 열지 않으며, 경합(사람이 마스킹 전에 로그인 페이지를
여는 것)이 원천적으로 없고, 붙기·종료 수단 같은 부품이 필요 없다.

(b) 는 로그인 시점에 표식이 켜지고 마스킹으로 되돌려야 하며, 그동안 인증 없는 디버깅 포트가 열려 있다. 유일한 우위였던
"로그인 브라우저에 chromedriver 가 붙지 않는다"는 **측정 가능한 차이로 나타나지 않았다.**

**다만 이것은 "잰 범위 안에서" 다.** 몰의 봇 방어가 우리가 재지 못한 축(TLS 지문·행동·IP 평판 등)을 보는지는 실사이트
없이 알 수 없다. 그 확인은 승인 대상이다.

### 참고 — "Selenium 로그인은 계속 실패했다"는 기록의 정체

이 저장소에는 로그인 경로가 오래 실패한 이력이 있다. 다만 그 원인은 **봇 차단이 아니었다** — DEVLOG(Phase 0A)는
배포본 로그에서 **이마트 프로모션 배너가 로그인 버튼을 덮어 `ElementClickInterceptedException`** 이 난 순간을 찾아
확정했고, 그 뒤 약 2개월간 모든 예약 수집이 건너뛰기로 끝났다. 그 밖에 SSG 빈 결과 행 파싱 실패·수집기 간 실패 전파도
같은 시기의 원인이었다. 전부 **자동화가 셀렉터로 직접 로그인하던 경로**의 문제이고, 사람이 타이핑하는 (a) 와는 다른 것이다.

그렇다고 (a) 가 안전하다는 뜻은 아니다. `Emart.signin` 에는 **reCAPTCHA 감지 후 즉시 실패**하는 분기가 있다 —
누군가 그 도전을 실제로 만났다는 뜻이다. 그 경로가 자동 로그인이었는지 사람 로그인이었는지는 코드로 알 수 없다.

## 아직 답이 없는 것

1. **(a) 의 지문이 순정과 완전히 같은가.** T2 는 `navigator.webdriver` 축에서 일치를 확인했지만 그 축뿐이다.
2. ~~**캡처 브라우저와 주입 브라우저의 User-Agent 가 다르다.**~~ → **해소.** UA 하드코딩을 제거해 두 브라우저가 같은
   실제 버전을 광고한다(위 참조). 다만 **실사이트에서 세션이 UA 에 묶이는지 자체는 여전히 미측정**이고, 이제는 두 값이
   같으므로 그 위험도 줄었다.
3. **`sanitize` 의 만료 필터가 실계정에서 필요한지.** ST-2 는 그 필터 **없이** 통했다. 지금은 방어적으로 넣어
   두었을 뿐 근거가 없다. 필요 여부는 같은 실행에 '필터 없는 팔'을 두어야 갈린다.
4. **세션 수명**(5-17) — 이관된 세션이 며칠 가는지. 5-10(만료 감지)의 설계 입력이다.
5. **스냅샷은 살아 있는 인증 토큰이다.** 지금 코드에는 디스크에 쓰는 경로가 **없다**(메모리까지만). 저장은
   암호화와 함께 온다(5-16). 프로필 경로를 저장하던 때보다 위험이 올라간다 — 프로필은 OS 계정에 묶였지만
   스냅샷은 파일 하나로 옮겨진다.

## 이번 측정에서 배운 것 (방법론)

- **대조군이 귀속을 갈랐다.** 처음엔 포트를 연 순정에서 `true` 만 보고 "런처가 뭔가 잘못됐나" 로 갈 뻔했다.
  같은 실행에 포트 없는 팔을 두자 원인이 포트로 확정됐다.
- **'재지 못함' 과 '재서 false' 를 같은 값으로 접으면 안 된다.** 첫 판 프로브는 보고를 못 받은 축을 `false` 로
  읽어, 재지도 않은 것에 대해 "ADR T2 와 어긋난다" 같은 강한 문장을 낼 수 있는 상태였다. 3상태로 갈랐다.
- **적대적 검증도 틀린다 — 측정이 가른다.** 검토가 "Windows Chrome 은 `lockfile` 을 만들지 않으므로 프로필
  사용 중 가드가 죽는다"를 HIGH 로 보고했다. 근거는 "쉬고 있는 프로필 14개에 파일이 없다"였는데, 실제로 띄워
  보니 도는 동안에는 파일이 있고 배타적으로 잠겨 있으며 종료 시 지워진다. **쉬고 있을 때 없는 것과 만들지
  않는 것은 다르다.** 지금은 그 전제를 프로브가 매번 함께 잰다.
